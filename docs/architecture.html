SOC Evidence Collector

Dokumen arsitektur & struktur aplikasi: aplikasi web untuk mengumpulkan evidence alert dari Elasticsearch / Elastic Security, melakukan triage, analisa, dan validasi IOC.

1. Tujuan & ruang lingkup

Masalah: saat alert masuk dan analis diminta evidence, data harus dicari lewat query manual atau berpindah-pindah halaman di Kibana.

Solusi: satu halaman yang, dari sebuah alert, langsung menampilkan IP, port, host, user, proses, file, hash, konteks MITRE, event terkait pada jendela waktu tertentu, hasil validasi IOC, lalu menyimpan verdict dan catatan analis, dan mengekspor semuanya sebagai laporan evidence.

  • Evidence collection: ekstraksi otomatis dari dokumen alert (ECS) + pivot ke log lain.
  • Triage: verdict (true positive / false positive / benign / perlu investigasi), catatan, dan opsional mengubah status alert di Kibana.
  • Analisa: tabel event terkait berdasarkan IP / host / user pada ±N menit dari alert.
  • Validasi IOC: VirusTotal dan AbuseIPDB (opsional), dengan cache dan perlindungan IP privat.

2. Arsitektur

Mengapa ada server perantara?

  • Browser tidak perlu (dan tidak boleh) memegang kredensial Elasticsearch / API key threat intel.
  • Membatasi query: server hanya membangun query terparameter yang sudah ditentukan, bukan meneruskan query bebas.
  • Menghindari masalah CORS dan memudahkan audit.

Mode demo

DEMO_MODE=true memakai server/demo.js (5 alert contoh bergaya Fortinet, Sangfor, dan M365 Defender, dengan IP rentang dokumentasi RFC 5737) sehingga UI bisa dicoba tanpa Elasticsearch. Hasil IOC pada mode ini adalah simulasi dan ditandai jelas di UI.

Frontend

Tanpa library. Semua UI dibangun dengan helper h() berbasis document.createElement dan textContent. Ini disengaja: data log berasal dari pihak yang tidak tepercaya (nama file, command line, user-agent, dsb.) sehingga tidak boleh disisipkan sebagai HTML.

Catatan versi: angka di tabel adalah rentang di package.json. Jalankan npm ls --depth=0 setelah npm install untuk melihat versi yang benar-benar terpasang, dan sesuaikan klien @elastic/elasticsearch dengan versi cluster Anda (mayor yang sama; mis. cluster 8.x → klien 8.x).

5. Endpoint API

MethodPathFungsi
GET/api/healthStatus server, koneksi Elastic, integrasi TI/Kibana yang aktif. Tidak perlu token.
GET/api/alertsDaftar alert. Query: from, to, severity, status, q (IP / teks), size (maks 200).
GET/api/alerts/:idDetail alert: evidence terstruktur, IOC, raw JSON, dan triage tersimpan.
POST/api/alerts/:id/relatedEvent terkait pada ±window_minutes (1-1440). Pivot default: semua IP, host, user pada alert.
GET/api/ioc?value=Validasi satu IOC (IP, domain, URL, MD5/SHA1/SHA256).
POST/api/ioc/bulkValidasi hingga 20 IOC sekaligus (berurutan, agar aman terhadap rate limit API gratis).
PUT/api/alerts/:id/triageSimpan verdict, catatan, dan opsional ubah status (diteruskan ke Kibana bila dikonfigurasi).
GET/api/alerts/:id/report?format=md|html|json&window=15Laporan evidence lengkap untuk diunduh / dilampirkan ke tiket.

6. Field yang dibaca

Aplikasi mengikuti Elastic Common Schema (ECS), sehingga log dari integrasi Fortinet, Sangfor, dan Microsoft 365 Defender yang sudah dinormalisasi ke ECS akan terbaca otomatis. Bila ada field khusus pada pipeline Anda, tambahkan di server/extract.js (FIELD_MAP dan fungsi extractEvidence).

7. Alur kerja analis

  1. Buka aplikasi, filter alert (waktu, severity, status, atau cari IP / host / user).
  2. Pilih alert: tab Evidence langsung menampilkan IP, port, host, user, proses, hash.
  3. Tab Event terkait: lihat aktivitas IP/host/user yang sama pada ±N menit.
  4. Tab Validasi IOC: cek reputasi IP, domain, hash, URL.
  1. Tab Triage: tetapkan verdict, tulis catatan, ubah status.
  2. Salin ringkasan untuk ditempel ke tiket, atau Export .md / .html / .json sebagai laporan evidence.

Verdict dan catatan tersimpan di data/triage.json dan ikut masuk ke laporan.

8. Keamanan

RisikoMitigasi di aplikasi
XSS dari data log (konten dikendalikan penyerang)UI memakai textContent (tanpa innerHTML); CSP dari helmet memblokir inline script; laporan HTML dan Markdown meng-escape semua nilai.
Injeksi query ElasticsearchQuery dibangun server dengan parameter terstruktur; IP divalidasi net.isIP; severity/status memakai daftar putih; input teks dibatasi 200 karakter dan memakai simple_query_string.
Kebocoran kredensialSemua kredensial di .env sisi server; error ke klien dibuat generik, detail hanya di log server.
Akses tanpa izinServer default bind ke 127.0.0.1; APP_TOKEN opsional (header x-api-token, perbandingan waktu-konstan); rate limit pada /api.
Kebocoran data internal ke pihak ketigaIP privat tidak pernah dikirim ke VirusTotal / AbuseIPDB. Domain dan URL internal bisa terkirim bila ikut menjadi IOC: tinjau sebelum mengaktifkan API key.
Akun Elastic berlebihanBuat API key khusus read-only pada index alert dan log yang dibutuhkan; untuk update status gunakan key Kibana terpisah dengan hak minimum.
Sebelum dipakai di jaringan: letakkan di belakang reverse proxy HTTPS (Nginx / Caddy), set APP_TOKEN atau autentikasi SSO di proxy, dan jangan set ES_TLS_REJECT_UNAUTHORIZED=false di produksi (gunakan ES_CA_CERT).
